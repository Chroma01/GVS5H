- **Problem reduction:** Minimum increments to make subarray [L,R] non-decreasing equals sum_{i=L}^{R} (runningmax(L..i) - a[i]) = S(L,R) - sum(L,R), where S is the sum of running prefix maxima. Final values must be >= running maxima (lower bound) and setting each position to its running maximum attains it.
- **Two pointers / monotonicity:** For fixed L cost is nondecreasing in R; for fixed R cost is nonincreasing in L. Hence the minimal valid L is nondecreasing in R: for each right, advance left while cost > k, then add right-left+1. A single element costs 0 <= k so left <= right always.
- **Next strictly greater chain:** Records setting running maxima from L are L, nxt[L], nxt[nxt[L]], ... with nxt[i] = first j>i having a[j] > a[i], else n (strict >, equal values do NOT start a new record). Compute right-to-left with a stack: pop while a[top] <= a[i].
- **Binary lifting for S(L,R):** up0[i]=nxt[i], add0[i]=a[i]*(nxt[i]-i); up[j][i]=up[j-1][up[j-1][i]], add[j][i]=add[j-1][i]+add[j-1][up[j-1][i]]. Query: p=L, s=0; for j from LOG-1 down to 0, if up[j][p] <= R then s += add[j][p], p = up[j][p]; then s += a[p]*(R-p+1). Sentinel index n: up[*][n]=n, add[*][n]=0; never jumped to because n > R.
- **Incremental cost (key speedup):** Appending an element only adds its own contribution: cost(l,r) = cost(l,r-1) + (max(a[l..r]) - a[r]); older running maxima are unchanged. Keep the window maximum in a monotonic deque (pop back while a[back] <= new). The full O(log n) S-query is needed only after each left increment (<= n times total), giving at most n queries instead of 2n.
- **Memory trim:** Store lifting tables as array('q') (int64) → about 27 MB for n=1e5, LOG=17, versus >100 MB with Python-int lists. All values (<= ~1e14) fit in signed 64-bit.
- **Complexity:** Preprocessing O(n log n) time and memory; each query O(log n); at most n queries; overall O(n log n). n=1e5 → ~4M inner operations.
- **Deque details:** Pop-back uses <= so a newer equal element dominates (stays in window longer). At most one front pop per left increment is ever needed because deque indices stay >= left and only old left can fall below it. Values are strictly decreasing front-to-back, so front is the window max.
- **Pitfalls:** strict > for records; sentinel absorbing in all levels; n=1 gives LOG=1, answer 1; cost arithmetic is Python big-int safe but int64 suffices.
- **Verified results:** Example 1 ([6,3,1,2,4,4], k=7) returns 17. Example 2 ([6,3,1,3,6], k=4) returns 12. Random brute-force agreement (n<=60, values<=20, k<=50, ~200 cases) found no mismatches; n=100000 run stays within time/memory limits.
- **Alternatives rejected:** O(n log^2 n) binary search per right; SWAG/monoid or segment-tree with lazy tags (front removal of running-max-sum is not a simple monoid); plain front-removal monotonic stack (needs re-deriving the suffix record chain, not amortizable).
