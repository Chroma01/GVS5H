- **Problem reduction:** Each adjacent swap at index i costs i. Optimal behavior is to fix values from largest (N) down to smallest. Before handling v, all values > v occupy positions v+1..N, so positions 1..v hold values 1..v in their original relative order. Value v sits at rank r_v = (count of values <= v at positions <= pos[v]) and must move right to position v.
- **Cost of value v:** Moving v from rank r_v to v costs sum_{i=r_v}^{v-1} i. With a_v = v - r_v = number of smaller values strictly to the right of v, cost = a_v(2v - a_v - 1)/2.
- **Answer:** Total = sum_v a_v(2v - a_v - 1)/2. Matches all samples: [3,2,1]->4, [2,4,1,3,5]->6, [1,2]->0.
- **Computing a_v:** Iterate v = 1..N; insert pos[v] into a Fenwick tree over positions 1..N. Let s = count of inserted (smaller) positions <= pos[v]; a_v = (v-1) - s. O(N log N).
- **Optimality argument:** Every sorting sequence crosses each inverted pair at least once and each swap resolves one crossing, so minimum-length (one swap per inversion) sequences are optimal. The largest-first schedule is such a reduced word; processing larger values first pushes smaller ones leftward, minimizing the indices at which later crossings occur. Each inversion pair crosses exactly once.
- **Brute-force checker design:** Swaps are symmetric (cost i either direction), so a single-source Dijkstra from the identity permutation over the permutation graph yields dist[P] = true minimum cost to sort P for all n! states at once. This avoids n! separate shortest-path runs. Implemented for n=2..7 (~5040 states max) with a heap.
- **Checker command:** run `python solution.py verify` to execute the exhaustive comparison for n=2..7 plus a reverse-sorted N=2*10^5 timing/answer check; no argument => solves from stdin normally.
- **Worst-case answer:** Reverse permutation gives a_v = v-1, cost_v = v(v-1)/2, so total = sum C(v,2) = C(N+1,3), ~1.333e15 for N=2e5. Checker asserts equality with math.comb(N+1,3).
- **Manual spot checks (formula vs. reasoning):** [3,2,1]->4; [2,4,1,3,5]->6; [4,3,2,1]->10 (greedy path costs 6+3+1); [2,4,3,1]->8; [2,3,1]->3, all consistent with construction.
- **Pitfalls:** cost index i is 1-based; count strictly smaller values (insert v only after querying a_v); r_v = v - a_v never negative; Fenwick bounds 1..N.
- **Complexity / overflow:** O(N log N) time, O(N) memory. Python big ints avoid overflow (C++ needs 64-bit; answer ~1.3e15).
