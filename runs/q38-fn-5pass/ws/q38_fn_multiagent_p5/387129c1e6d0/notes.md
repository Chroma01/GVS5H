- **Implemented approach:** Simulate the whole path, collect every traversed horizontal segment as an inclusive interval on its y-coordinate and every vertical segment as an inclusive interval on its x-coordinate. Merge intervals per line, then test each house against merged horizontal intervals first and vertical intervals only if not already covered.
- **Segment storage:** During simulation, `horiz[y]` stores `(x_left, x_right)` intervals and `vert[x]` stores `(y_low, y_high)` intervals. Moves are processed in order, updating the current position after appending the segment. Endpoints are included because the stored intervals are inclusive.
- **Merging details:** For each line, intervals are sorted by left endpoint and merged when the next interval starts at or before `current_right + 1`. The `+1` is safe because all house coordinates are integers: if two integer intervals are adjacent like `[0, 1]` and `[2, 3]`, there is no integer point in the continuous gap. After merging, each line maps its fixed coordinate to `(starts, ends)` lists.
- **Counting details:** For a house `(hx, hy)`, binary search the merged horizontal intervals on line `hy` for the last interval whose start is at most `hx`, then check whether its end is at least `hx`. If covered, count it and skip vertical checking. Otherwise, perform the same check on vertical intervals for line `hx`. This counts each visited house exactly once, including houses at horizontal/vertical intersections.
- **Complexity:** Simulation is O(M). Sorting and merging all interval lists costs O(M log M) in total. Counting all houses costs O(N log M) in the worst case. Memory is O(N + M). Python integers safely handle final coordinates up to about 2e14.
- **Edge cases:** Repeated or overlapping segments are merged. Turning points are included because adjacent segments share inclusive endpoints. Houses at intersections are counted once due to horizontal-first checking. Negative coordinates and very large coordinates are handled naturally. The constraint that there is no house at the start is not relied upon except that the code would also count it if it existed and lay on a traversed segment.
- **Performance choices:** Input is read with `split()` and parsed by index, then the token list is deleted before merging/counting. Merged intervals are stored as separate `starts` and `ends` lists so `bisect_right` operates on integer lists rather than tuple lists. Local bindings for `get` and `bisect_right` reduce lookup overhead in the counting loop.
