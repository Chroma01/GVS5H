- **Problem:** permutation P of 1..N; swapping P_i,P_{i+1} costs i; min total cost to sort ascending. N<=2e5.
- **Adopted formula:** answer = sum over values v of (I_v * pos[v] - I_v*(I_v+1)//2), where pos[v] is the 1-indexed original position and I_v = number of values larger than v appearing before v originally. Equivalently sum_{k=1}^{I_v}(pos[v]-k).
- **Derivation (upper bound):** left-to-right insertion sort. When the element v at original position pos[v] is processed, the prefix is sorted and the larger-before elements sit at its right end, so v walks left exactly I_v boundaries pos[v]-1, pos[v]-2, ..., pos[v]-I_v. Total = I_v*pos[v] - I_v(I_v+1)/2. Every swap fixes one inversion, so the whole run uses the minimum possible swap count.
- **Why leftward, not rightward:** the dual (charge moves right, J_v = smaller elements after v) overestimates: for sample 2 it gives 4+5=9 versus true 6. Costs grow with boundary index, so charging inversions to leftward walks (cheaper boundaries) is what is optimal.
- **Exhaustive validation:** Dijkstra over the full permutation graph for every N from 2 to 7 (nodes = permutations, edges = adjacent swaps weighted by boundary i, 1-indexed), comparing the true minimum against the formula. Every permutation matched; no counterexample found. Spot confirmations incl. 321->4, 24135->6, 12->0, 4321->10, 54321->20, 4132->8, 2431->8, 35142->15, 231->3, 312->3.
- **Lower-bound intuition:** boundary j must be crossed at least R_j = #{values<=j lying in positions>j} times, and total swaps >= INV. The relaxed bound sum_j j*R_j + max(0, INV - sum R_j) is valid but sometimes loose: for 4132 it gives 7 (true 8) and for 35142 it gives 13 (true 15), because surplus swaps cannot always sit on boundary 1 (a boundary-j swap needs neighboring-boundary swaps to recreate inversions). The insertion formula equals the true optimum in every tested case.
- **Disproven naive bounds:** the boundary-count bound sum i*d_i (= sum_j j*R_j) returns 3 for 321 but the answer is 4. A tempting "sum over inversions of min(pos)" returns 5 for sample 2 but the answer is 6. Do not use either.
- **Implementation:** Fenwick tree over values 1..N, scan positions left to right. At 0-indexed idx (p=idx+1), le = pref(v) = already-seen values <= v, I = seen - le; add I*p - I*(I+1)//2; then insert v. O(N log N) time, O(N) memory.
- **Pitfalls:** boundaries are 1-indexed (p=idx+1); le counts values <= v which equals count < v since values are distinct; contributions reach ~N^3/6 ~ 1.3e15 for N=2e5 so Python big ints are required/used; I_v must count only already-scanned (left) elements.
- **Edge cases:** already sorted -> 0; N=2 [2,1] -> 1; N=2 [1,2] -> 0.
