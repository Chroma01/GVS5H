- **Core identity:** For a point assignment at cell x, only paths through x change. If `pref` is the sum of products from start to predecessors of x, and `suf` is the sum from successors of x to goal, then `ans += (new-old) * pref * suf`. This avoids division and handles zeros naturally.
- **DP definitions:** Use column-major flat arrays. `L[c]` is forward DP entering column c (`F[:, c-1]`), with `L[0]=e_0`. `R[c]` is backward DP inclusive in column c (`G[:, c]`), with `R[N]=e_{K-1}`. Full precomputation is O(HW).
- **Lazy state:** At current column c, maintain `L[0..c]` fully correct and `R[c+1..N]` fully correct. Current forward vector `L[c+1]` is correct only on prefix `[0, f_valid)`. Current backward vector `R[c]` is correct only on suffix `[rv_valid, K)`.
- **Update:** Before changing A[r,c], ensure forward up to r-1 and backward from r+1. These ensured parts do not depend on A[r,c]. Compute delta, assign A, then conservatively set `f_valid=r`, `rv_valid=r+1`. If the assigned value equals the old value, do nothing; stale intervals remain valid because the grid did not change.
- **Horizontal moves:** `move_right` finalizes `L[c+1]` from `f_valid` and simultaneously computes `L[c+2]` in one top-down pass. Then c++, `f_valid=K`, `rv_valid=0`. `move_left` finalizes `R[c]` from `rv_valid` and simultaneously computes `R[c-1]` in one bottom-up pass. Then c--, `f_valid=K`, `rv_valid=0`.
- **Vertical moves:** Only r changes. Ensures during later updates are amortized by cursor movement; even no-op moves can delay ensures, but the total recomputed distance is bounded by the number of vertical moves since the last relevant change.
- **Orientation optimization:** The expensive operation is a horizontal move scanning the row dimension. Count original L/R and U/D. If not transposed, horizontal moves are L/R and rows=H. If transposed, horizontal moves are U/D and rows=W. Choose orientation minimizing `rows * horizontal_count`, tie by smaller rows. This keeps worst-case horizontal scans around `Q*HW/(H+W)`, at most about 4.5e7 row iterations under HW<=2e5.
- **Transposition mapping:** If transposed, new coordinates are `(old_w, old_h)`. Original L/R become vertical moves; original U/D become horizontal moves. The grid stored as original row-major is already column-major for the transposed orientation.
- **Implementation details:** Use flat lists, local variables, conditional subtraction for sums below 2*MOD, and `% mod` only after products. Boundaries are handled by `L[0]` and `R[N]`. The answer is maintained modulo 998244353 and printed after each query.
- **Complexity:** O(HW + Q + K * chosen_horizontal_count) time, O(HW + K) memory, where K is the chosen row count.
