- **Problem:** Given binary string `s` and `numOps` flips, minimize the longest run of identical characters. n <= 1000.
- **Approach:** Minimax -> binary search on candidate answer L in [1, n]. Feasibility is monotone in L, so standard lower-bound binary search returns the smallest feasible L.
- **Feasibility for L >= 2:** Sum `len // (L+1)` over each maximal run of length `len`; feasible iff total <= numOps.
- **Why `len // (L+1)` is exact for L >= 2:** Lower bound: pick the len positions of a run; if t are flipped, the remaining len - t same-char bits form at most t+1 blocks, each of length <= L, so len - t <= (t+1)L, giving t >= (len-L)/(L+1) = floor(len/(L+1)). Construction (tight): write len = q(L+1)+r with q = floor(len/(L+1)); place q flips strictly interior so the len-q original bits split into q+1 blocks each in [1, L] (needs qL + r <= (q+1)L i.e. r <= L, and each block >= 1 which holds for L >= 2). Interior placement keeps each separator isolated (length 1) and never merges with the neighboring opposite run, so per-run costs are independent and summable.
- **L = 1 is special and MUST be handled separately:** run-sum formula is not tight (lower bound only). Counterexample `"0110"`: run-sum = floor(2/2) = 1, but true cost is 2. For L = 1 the string must be perfectly alternating, so cost = min Hamming distance to `"0101..."` and `"1010..."`, which equals `min(m1, n - m1)` since the two patterns are complements.
- **Binary search:** `lo=1, hi=n`, `mid` feasible -> `hi=mid` else `lo=mid+1`. n = 1 returns 1 directly through this.
- **Complexity:** O(n log n) time, O(1) extra space.
- **Edge cases verified:** n = 1 -> 1; numOps = 0 -> original max run; numOps = n -> 1; already-alternating -> 1.
- **Empirical verification:** Brute force (all 2^n flip subsets, min-max-run prefix over flip counts) compared against the solution for ALL binary strings of length 1..9 across all numOps in [0, n]. Result: PASS, zero mismatches (~11k comparisons).
- **Corrected test expectations:** `"0110", numOps=1 -> 2` (was wrongly 1); `"0000000000" (10 zeros), numOps=3 -> 2` (was wrongly 3). Official examples confirmed: `"000001",1 -> 2`, `"0000",2 -> 1`, `"0101",0 -> 1`.
- **Superseded ideas:** Do NOT apply the run-sum formula at L = 1 (disproven by `"0110"`). Priority-queue "split longest run" greedy is unnecessary; monotone binary search + run formula is already optimal.
