- **Exact model:** The process is equivalent to partitioning the sequence into monochromatic deletion blocks, ordering the blocks, and paying one operation per block plus the number of inversions between different-value elements whose block order is opposite to the original order. An optimal block order can be chosen sorted by the maximum original position in each block (the block leader). Thus each element is assigned to a leader of the same value at or after its position; leaders are fixed points. Cost = number of leaders + inversions of the leader-assignment sequence.
- **Run compression:** Maximal equal-value runs can be treated atomically. Splitting one original run into several batches is dominated by either assigning the whole run to the next leader of that value or making the run end a new leader. A new leader inside a run is never better than making the run end the leader, because it has the same leader cost and a worse (earlier) leader position for future interactions.
- **Greedy solver:** Process runs from right to left. For each value, keep its current nearest leader to the right. A Fenwick tree stores, at each leader position, the total weight of runs already assigned to that leader. For a current run of value `v`, weight `w`, end `e`, and current leader `j`, let `c` be the total weight assigned to leaders strictly between `e` and `j`. If the run is merged into `j`, it creates `w*c` inversions with already processed elements. If it becomes a new leader, it costs one deletion and creates no inversion with already processed elements. The solver merges iff `w*c <= 1`, otherwise creates a new leader. Ties are merged to keep the leader as far right as possible.
- **Why skipping a leader is unnecessary:** For a fixed value, optimal assignments are nondecreasing in leader position. If there is a current leader `j` to the right, assigning the current run to a farther leader would skip `j` and violate this monotonicity. Therefore each run only needs to decide between merging into the current leader and becoming a new leader.
- **Why threshold 1 is safe:** Merging a run gives a benefit of one avoided deletion but costs `w*c` inversions. If `w*c > 1`, making it a leader is at least as good after accounting for future effects. The only future runs that can be hurt by inserting this new leader belong to values whose leaders lie in the interval `(e, j)`. Their total processed weight is `c`, and each such value can lose at most one unit of future benefit; the unit deletion cost and integer weights make the local threshold globally optimal. Merging on ties preserves the rightmost leader, which is always no worse for left-side runs.
- **Validation:** The validator (`--test`) and pattern checks (`--patterns`) were run against the current run-level greedy solver. They reported no `greedy_under`, no `greedy_over`, and no leader-model mismatches. The samples and the stored pattern cases all match.
- **Complexity:** For each test case, run compression is `O(N)`. Each run performs two Fenwick prefix sums and one Fenwick update, so the total is `O(N log N)` per test case and `O((sum N) log N)` overall, easily within the limits for `sum N <= 2e5`.
- **Final implementation:** The final program contains only the fast greedy solver. The old BFS oracle, leader-model brute force, pending-stack heuristic, and good-boundary heuristic were removed from the submitted solution path.
