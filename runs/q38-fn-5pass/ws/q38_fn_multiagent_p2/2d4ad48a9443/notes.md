- **Sample tests:** Manual verification of the provided examples gives 17 and 12. Random small brute-force reasoning found no mismatch; no bug was identified in the current implementation.
- **Core formula:** For a subarray, the minimum increments needed to make it non-decreasing is obtained greedily by setting each final value to the maximum original value seen so far. Thus cost(l, r) = sum_{i=l..r} (max(nums[l..i]) - nums[i]).
- **Record decomposition:** For a fixed left endpoint, the prefix maximum changes only at positions reached by repeatedly taking the next strictly greater element to the right. Between a record position i and nxt[i] - 1, the prefix maximum is constant and equal to nums[i].
- **Segment cost:** The full cost of record segment [i, nxt[i] - 1] is nums[i] * (nxt[i] - i) - sum(nums[i:nxt[i]]). This is precomputed as cost0[i].
- **Binary lifting:** up[j][i] gives the node after 2^j next-greater jumps. jumpcost[j][i] stores the sum of full segment costs for those jumps. To query cost(l, r), jump from l while the landing node is <= r, accumulating full segment costs. The remaining current record cur has nxt[cur] > r, so add the partial segment cost [cur, r].
- **Query correctness:** Use landing node <= r, not < r, because if the next record is exactly r, the previous segment is complete and r starts a new one-element partial segment. The sentinel n is never jumped to because r < n.
- **Counting:** cost(l, r) is non-decreasing when r increases and non-increasing when l increases. Therefore a two-pointer scan over right endpoints works: maintain the smallest left such that cost(left, right) <= k, then all starts from left to right are valid.
- **Early exit:** During a cost query, all segment costs are non-negative. If the accumulated total exceeds k, the subarray is already invalid and the query can return False immediately.
- **Implementation choices:** next-greater indices are built with a monotonic stack popping values <= current to enforce strict greater. up tables are stored as Python lists for faster indexing, while jumpcost tables use array('q') to reduce memory. Prefix sums remain Python lists.
- **Complexity:** Preprocessing is O(n log n) time and memory. Each cost query is O(log n). The two-pointer loop performs O(n) successful queries and O(n) failed queries, so total time is O(n log n), with log n around 17 for n = 1e5.
- **Edge cases:** Equal values are handled by strict next-greater logic. Single-element subarrays always have cost 0. Large answers fit Python int. Maximum theoretical cost is about 1e14, safely within signed 64-bit storage.
- **Pitfalls checked:** Do not use next greater-or-equal; equal values should stay in the same prefix-maximum segment. Do not jump to sentinel n. The final partial segment must use the current record value, not the original left value.
