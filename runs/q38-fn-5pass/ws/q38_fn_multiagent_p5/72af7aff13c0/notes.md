- **Core invariant:** Maintain forward DP `F` and backward DP `B` lazily relative to the cursor `(r,c)`. `F` rows above `r` are fully correct, and row `r` is correct on prefix `0..c`. `B` rows below `r` are fully correct, and row `r` is correct on suffix `c..W-1`. Rows outside these regions may be stale.
- **Answer update:** Changing cell `(x,y)` from `old` to `new` changes the total path sum by `(new-old) * F_excl(x,y) * B_excl(x,y)`, where `F_excl` is the weighted path sum from start to the cell excluding its value, and `B_excl` is the weighted path sum from the cell to end excluding its value. Start/end have exclusive value `1`.
- **Move costs:** Horizontal moves need only recompute the new cell's `F` and `B` values, so they are O(1). Vertical moves require restoring a full row on one side: moving down makes the old row `F`-full, moving up makes the old row `B`-full. Each vertical move costs O(W) in the chosen orientation.
- **Orientation choice:** The grid may be transposed. In the chosen orientation, only vertical cursor moves are expensive. Estimate original cost as `#(U/D) * (W-1)` and transposed cost as `#(L/R) * (H-1)`, choosing the smaller. On ties, prefer fewer vertical moves. This is important when the cursor mostly moves along one axis.
- **Direction mapping under transpose:** Original `(h,w)` becomes `(w,h)`. Directions map as L->U, R->D, U->L, D->R. Cursor coordinates also swap.
- **Segment recomputations:** For vertical moves, recompute only the necessary row segment before the value change to make `F_excl` or `B_excl` valid, then after the change recompute the affected segment to restore the invariant. Down: recompute new row `F` prefix before update, old row `F` suffix after update. Up: recompute new row `B` suffix before update, old row `B` prefix after update.
- **Full-row flags:** Conservative boolean arrays `f_full` and `b_full` track rows known to be fully correct for `F` or `B`. They allow skipping some O(W) segment recomputations when a row is already full. True is always safe; False may be conservative and cause extra work but never incorrectness.
- **Boundary handling:** `F` uses a virtual source at `(0,0)` via special-casing the first row/column. `B` uses a virtual value `1` only at the bottom-right end, handled by special-casing the last row/column in point and segment recomputations.
- **Complexity:** Initial DP is O(HW). Each query is O(1) for horizontal moves and O(W) for vertical moves in the selected orientation. With `HW <= 200000`, the worst practical loop count is around `Q * sqrt(HW) / 2`, and orientation selection often reduces it substantially.
- **Implementation details:** Use row lists for `A`, `F`, `B`. Keep modulo operations local and reduce sums with one conditional subtraction before multiplication. Store queries offline to choose orientation. Use flat direction integers for speed.
