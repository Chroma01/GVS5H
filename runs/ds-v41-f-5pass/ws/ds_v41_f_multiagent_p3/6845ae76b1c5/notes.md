- **Problem:** answer for each query (X,Y) the sum over i<=X, j<=Y of |A_i-B_j|; N<=1e5, K<=1e4, values<=2e8.
- **Decomposition:** write X = P*S + r with P=X//S. The P full A-blocks [0,S),[S,2S),... are always full (even when N not divisible by S, since P*S<=N). The remaining r = X-P*S elements A[P*S:X) form the partial suffix.
- **Full-block precompute:** for each block b, w_j = sum_{a in block}|a-B_j| computed vectorized: k=searchsorted(sorted_block,B,'right'), w = B*k - ps[k] + (total-ps[k]) - B*(S-k). cum=np.cumsum(w); contribution at prefix Y is cum[Y-1]. Accumulator C indexed by distinct query-Y is updated block by block; queries with P==b read C just before block b is added, so they get blocks 0..b-1. This is O((N/S)*N) numpy element-ops.
- **Partial suffix:** offline sweep over Y (queries sorted by Y). Fenwick over value-compressed B stores count and sum of B[0:Y). Insert B in batches with np.add.at on precomputed update-path nodes (updates are additive, so batching is valid). For each query's partial elements compute r=rankA, then vectorized Fenwick prefix query over r; h = 2*a*cnt - 2*sum + S_Y - a*Y equals sum_j|a-B_j|. Per-element contributions summed per query via np.add.reduceat over segment lengths.
- **Block size:** S chosen from balance c1*N^2/S vs c2*K*S; using S = N*sqrt(0.28/K) (capped to [1,N]) gives ~530 for N=1e5,K=1e4 and larger S when K is small.
- **Memory/chunking:** partial elements are processed in chunks of <=2^20 so a single Y-group of many queries does not blow memory. Zero-length suffixes are filtered (needed for reduceat correctness).
- **Overflow:** all arithmetic in int64; worst-case answer N*N*2e8 = 2e18 < 9.2e18, fits.
- **Pitfalls:** searchsorted 'right' for counting values <= a; distinctY-1 for prefix index (first Y elements); queries with P==0 correctly get 0 full-block contribution; block slice l+S<=N guaranteed for b<maxP.
- **Complexity:** O((N/S)*N*log(S) + (K*S)*logN) with numpy vectorization, plus O(N log m) batched Fenwick insertions.
