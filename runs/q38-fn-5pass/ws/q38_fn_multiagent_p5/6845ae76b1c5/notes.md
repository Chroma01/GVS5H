- **Approach:** Use index-block decomposition. Choose number of blocks `nb ~= sqrt(K/2)` and block size `S = ceil(N/nb)`. For max constraints this gives `nb ~= 71`, `S ~= 1400`, balancing precomputation `O(N*nb)` and query partial work `O(K*S)`.
- **Pref tables:** `prefA[ba]` is a flat `array('q')`. Row `p-1`, column `q` stores sum over first `p` elements of A-block `ba` and first `q` full B-blocks. `prefB` is symmetric. This makes `partialA-fullB` and `fullA-partialB` O(1).
- **Building pref tables:** For each element in an X-block, evaluate `sum |x - Y_j|` for every full Y-block using sorted block values and prefix sums with `bisect_right`. Maintain cumulative columns in a Python list, fill a temporary Python list row-by-row, then convert once per block to `array('q')`. This is faster than many `array` assignments or repeated `extend` calls.
- **Block sums:** `block_pref[i][j]` is the 2D prefix of full block-pair sums. It is derived from the last row of each `prefA[ba]`, where differences over B-block prefix columns give individual block-pair sums.
- **Query decomposition:** For query `(X,Y)`, let current A-block be `ba` with local prefix `p`, current B-block be `bb` with local prefix `r`. Answer is:
  `full-full + partialA-fullB + fullA-partialB + partial-partial`.
  Full-full is `block_pref[ba][bb]`. Partial-full terms are direct pref-table lookups.
- **Partial-partial:** For the current two prefixes, sort the smaller prefix (or use its precomputed sorted full block if it is full), build prefix sums, and binary-search it for each element of the larger prefix. Special cases: very small rectangles use direct double loop; size-1 side scans the other side or uses a full sorted block formula. Exact `(ba,p,bb,r)` results are cached.
- **Boundary handling:** Prefix lengths are always at least 1. If a query ends exactly at a block boundary, that block is treated as the partial block with `p = block_len`, while `fullA`/`fullB` count only earlier blocks. This keeps the decomposition disjoint and correct.
- **Memory:** Two pref tables dominate: about `2*N*(nb+1)` signed 64-bit values, roughly 115 MB at max constraints. Sorted blocks and prefix sums add moderate overhead. Temporary Python buffers per block are small and freed.
- **Complexity:** Precomputation is about `O(N*nb*log S)` due to bisect inside block evaluation, with `nb ~= sqrt(K)`. Query time is O(1) plus partial-partial `O(min(p,r) log max(p,r))` in the implemented sort-smaller strategy, bounded by about `O(K*S log S)` worst-case but typically much lower due to block size tuning and caching.
- **Edge cases:** Works for `N=1`, `S=1`, last short blocks, duplicate values, zero values, and queries ending at block boundaries. Answers fit in signed 64-bit, but Python integers are used for arithmetic and only stored in `array('q')` after conversion.
