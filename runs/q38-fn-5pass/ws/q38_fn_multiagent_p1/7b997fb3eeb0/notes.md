- **Core characterization:** For an interval `[L, R]` of length `m`, `k` pairs are possible iff the `k` smallest mochi in the interval can be paired with the `k` largest mochi. This follows from an exchange argument: replacing tops by smaller mochi and bottoms by larger mochi never hurts feasibility.
- **Feasibility predicate:** Let `f(i)` be the first index `j` such that `A[j] >= 2*A[i]`. For `k` pairs, pairing top `L+t` with bottom `R-k+1+t` is necessary and sufficient, so we need `f(L+t) <= R-k+1+t` for all `t=0..k-1`. With `B[i] = f(i)-i`, this is equivalent to `max_{i=L}^{L+k-1} B[i] <= m-k`.
- **Precomputing `f`:** Because `A` is sorted and `2*A[i]` is nondecreasing, a two-pointer scan computes all `f(i)` in `O(N)`. If no valid `j` exists, use sentinel `f(i)=N`, giving `B[i]=N-i`. This sentinel correctly fails the predicate for every valid `k` because it would imply `N <= R+t-k <= N-1`.
- **Sparse table:** Build a static range-maximum sparse table over `B`. `st[k][i]` stores the maximum of `B[i .. i+2^k-1]`. Build rows using a list comprehension with `zip(prev, prev[step:])` for speed.
- **Query handling:** For each query, binary search `k` in `[0, m//2]`. The cap `m//2` is essential to keep top and bottom sets disjoint. For a candidate `mid`, query the maximum on `[L, L+mid-1]` using two overlapping sparse-table blocks. Feasibility is `max <= m-mid`.
- **Monotonicity:** As `k` increases, the range maximum is nondecreasing and `m-k` is decreasing, so feasibility is monotone. Binary search is valid.
- **Correctness summary:** The exchange argument reduces matching to pairing smallest tops with largest bottoms. The `B` predicate exactly encodes those pairings. Sparse table gives `O(1)` predicate checks, and binary search finds the maximum feasible `k`.
- **Complexity:** Precomputation `O(N log N)`, queries `O(Q log N)`, memory `O(N log N)`. With `N, Q <= 2e5`, this is intended to fit in Python with optimized loops and fast I/O.
- **Implementation details:** Use 0-based indexing internally. Read all integers at once, slice queries, and delete `A` and the original input list before building the sparse table to reduce peak memory. Use local variable bindings in the query loop for speed.
- **Pitfalls checked:** Off-by-one in `R-k+1+t`, sentinel handling, forgetting the `m//2` cap, sparse-table row bounds, and overlapping RMQ blocks.
